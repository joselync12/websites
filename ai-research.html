Hybrid AI-Powered Phishing Detection and Explanation System

Combining a machine learning classifier with an AI explanation assistant

Research Topic

My research topic is Hybrid AI-Powered Phishing Detection and Explanation System. This project builds on my earlier machine learning phishing detection work and my AI digital person / chatbot, combining them into a single system that both detects suspicious websites and explains its reasoning in plain language.

Assignment 6 — completed research. The classifier comparison and the hybrid explanation experiment described below were actually run; their measured results appear in the Results section. What remains future work (a user study) is labeled as such in Limitations.

Problem Statement

Phishing websites continue to trick users by imitating legitimate pages. Machine learning models can flag suspicious URLs with good accuracy, but a bare "phishing / legitimate" label does not tell the user why a website was flagged. Users who do not understand the reasons behind a warning are more likely to ignore it, click through it, or distrust future warnings entirely.

At the same time, an AI chatbot can generate helpful explanations, but on its own it cannot reliably judge whether a specific URL is dangerous. The gap is that detection systems lack explainability, and explanation assistants lack a trustworthy detection signal to anchor their answers.

Research Question

Can adding a grounded AI explanation to the Random Forest phishing detector make its predictions easier to interpret while keeping the classifier's predictions unchanged?

Note the two parts of the question: easier to interpret (the thing being improved) and predictions unchanged (the thing that must not regress). The improvement is deliberately about interpretability, not about raising classification accuracy.

Research Objectives

  1. Reproduce a trustworthy baseline: train and evaluate Decision Tree and Random Forest classifiers on URL features from the Web Page Phishing Dataset, and verify the results against my earlier phishing detection project.
  2. Run a fair model comparison — Logistic Regression, k-Nearest Neighbors, Gradient Boosting and SVM against the two baselines on the same group-based split, with 5-fold cross-validation for stability.
  3. Build the hybrid system: keep the real Random Forest as the sole decision-maker and add an AI explanation assistant (Cloudflare Worker + Gemini) that translates the model's own votes and feature contributions into plain language.
  4. Verify the predictions-unchanged property: confirm that adding the explanation layer never alters the classifier's output, by checking the JS inference against scikit-learn on held-out rows and confirming the Worker returns only prose, never a verdict.
  5. Measure explanation grounding — whether the generated explanations are actually supported by the model's votes and contributions — plus response time and failure rate.
  6. Document security controls against XSS and prompt injection that this hybrid design requires, and test them with a malicious HTML/script string.
  7. State the limitations honestly, including what this experiment cannot prove (it is not a user-comprehension study).

Hybrid AI Method

The system combines two components that already existed separately in my projects: a machine learning phishing classifier (Random Forest) and an AI explanation assistant (the Cloudflare Worker + Gemini backend from my chatbot / digital person work). The classifier is the only decision-maker; the assistant never classifies — it only explains numbers it is handed.

The design principle is grounded explanation: the AI is given the model's actual output (predicted class, phishing probability, tree vote split, and per-feature contributions) and is instructed to use only those numbers. This is what keeps the classifier's predictions unchanged — the AI has no ability to change them, because it sits strictly after the model in the pipeline.

  1. User submits a URL through the phishing detection web interface.
  2. Feature extraction — the same 19 numeric URL features used in training are computed in the browser (length, dots, hyphens, slashes, redirection markers, and so on).
  3. Random Forest classification — the real exported model (100 decision trees, serialized from the scikit-learn pipeline) is walked tree by tree in the browser. This produces the verdict, the probability, the vote split, and the per-feature contribution deltas.
  4. AI explanation (opt-in) — only when the user clicks "Explain This Prediction", the model's output is sent to the Cloudflare Worker, which re-validates it against a strict schema and a whitelist of the 19 feature names, then asks Gemini to explain it in plain language.
  5. Output to user — the verdict card stays exactly as the model produced it, and the explanation is rendered beside it as plain text via textContent. If Gemini or the Worker fails, the verdict is untouched and a safe error message appears in the explanation panel only.

The Worker holds the Gemini API key server-side; no key is ever embedded in the front end. The Worker never visits or fetches the URL being explained.

Baseline Model

The baseline is my earlier phishing detection work, which trained two scikit-learn classifiers — a Decision Tree and a Random Forest — on the 19 URL features from the Web Page Phishing Dataset. Both were re-trained and re-measured for this assignment on the identical group-based split, and both reproduced my earlier accuracies exactly (delta = 0.0), which is the honest verification that the baseline is stable before I build anything on top of it.

Proposed Improvement

The improvement over the baseline is an interpretability layer, not a higher accuracy score. The Random Forest's classification is deliberately left untouched — the same model, the same 100 trees, the same verdict. What changes is that the user now also gets a plain-language explanation grounded in the model's own reasoning:

  • Surfaces the specific URL features that contributed to the prediction, with their real contribution deltas
  • Translates those numbers into plain-language reasoning a non-expert can follow, via Gemini through the existing Worker
  • Keeps the raw verdict permanently visible, independent of whether the AI explanation succeeds
  • Stays opt-in: the explanation is only requested when the user asks for it, so the classifier path never depends on the network

Because the improvement is interpretability, the honest way to evaluate it is not "did accuracy go up" — it cannot, since the classifier is unchanged by design. The meaningful questions are: (1) are the explanations actually supported by the model's real votes and contributions, and (2) does adding them leave the classifier's predictions byte-for-byte identical? Both are measured in the experiment below.

Experimental Methodology

Two experiments were run. The first compares classifiers to establish the baseline; the second tests the hybrid explanation layer itself. Both are reproducible from this repository (see Reproducibility below).

Experiment 1 — Classifier comparison (notebook)

  1. Dataset preparation — load the Web Page Phishing Dataset (100,077 rows), remove exact duplicates (78,186 removed → 21,891 remaining), and split with a group-based shuffle so rows sharing an identical feature vector never appear on both sides of the split (17,523 train / 4,368 held-out test).
  2. Baseline replication — re-train Decision Tree and Random Forest and assert their accuracies match the Midterm reference values exactly (81.41% and 82.58%, delta 0.0). This is a verification gate, not a copied number.
  3. Additional models — train Logistic Regression, k-Nearest Neighbors, Gradient Boosting and SVM on the same split, recording accuracy, precision, recall, F1, training time and prediction time.
  4. Stability check — run 5-fold cross-validation on every model so the single-split numbers can be seen in context.
  5. Fairness — all models see the identical cleaned data, the identical split, and the identical features. No model is tuned harder than another.

Experiment 2 — Random Forest alone vs Random Forest + AI explanation

Because the improvement is interpretability, this experiment tests grounding rather than accuracy. It uses 10 held-out test rows (a deterministic selection: every 4th row of the 40-row held-out fixture set, chosen so the run is reproducible) spanning both predicted classes and probabilities from 0.13 to 0.99.

  1. Condition A — Random Forest alone. The real exported model runs in the browser's inference path and produces a label, a probability, a tree vote split and per-feature contribution deltas. No explanation exists in this condition.
  2. Condition B — Random Forest + AI explanation. The same model output is sent to the deployed Worker (mission-comms-chatbot), which validates it and asks Gemini to explain it. The verdict itself is computed locally before any network call, so it cannot be altered by the explanation.
  3. Correctness gate — before sending anything, the JavaScript inference result is checked against the prediction scikit-learn recorded for that same held-out row. This proves the explanation is grounded in real model output, not a re-implementation.
  4. Grounding measurement — each explanation's text is checked automatically against the model's real output: does it name at least one of the model's actual top contributing features? Does its verdict language agree with the predicted class? Does it avoid claiming to have visited the URL? Does it carry the required "not proof of safety" caveat?
  5. Unchanged-prediction check — the Worker's response is inspected to confirm it contains only prose (a reply field) and no verdict field, proving the classifier's prediction is untouched by the explanation layer.
  6. Cost measurement — response time per example, and any failures (network errors, Gemini overload, empty replies), are recorded as they actually occurred.

The grounding checks are automated lexical comparisons between the explanation text and the model's real numbers. They show whether the text is consistent with the model. They are not a user study and do not demonstrate improved human comprehension — see Limitations.

Reading these results honestly. The automated lexical checker undercounted grounding because of phrasing differences: it reported only 4/6 verdict agreement and 1/6 caveat presence, but reading all 6 explanation texts shows the true figures are 6/6 and 6/6. For example, the two apparent "disagreements" both correctly said the URL was classified as phishing; the checker was falsely tripped by the required caveat phrase "not absolute proof that the website is safe or dangerous," which contains the substring "is safe." This is exactly why the table reports the manually verified numbers alongside the raw automated ones, and it is a limitation of the automated metric noted below — not a defect in the explanations.

XSS Security Controls

This hybrid system accepts a user-submitted URL and displays AI-generated text, so it carries two distinct injection risks. Below I walk through each one as: the security problem, the control I implemented, how it mitigates the risk, and what would further improve it.

Risk 1 — Untrusted URL as a payload

Security problem. The URL a user types is attacker-controlled. If it were ever inserted into the page as HTML, a string such as <img src=x onerror=alert(1)> or <script>…</script> would execute in the browser — a cross-site scripting (XSS) vulnerability that could steal session tokens, deface the page, or redirect the visitor.

Security control. Untrusted strings are written with textContent, never innerHTML. The explanation renderer builds DOM nodes with document.createElement() and assigns the reply via textContent only.

Mitigation. textContent treats its input as literal text and never parses markup, so a malicious string is displayed as visible characters rather than executed. A dedicated test feeds a real <script>/<img onerror> payload into the renderer and asserts that (a) the text appears verbatim and (b) innerHTML was never assigned on the container or any child element. That test passes.

Security improvement. A Content Security Policy that disables inline scripts would add defence-in-depth, so that even if a markup injection slipped through somewhere, an injected script still could not execute.

Risk 2 — AI-generated text as a payload

Security problem. The explanation text is produced by a large language model reacting to attacker-influenced input. A crafted URL could try to make the model emit markup or instructions ("ignore previous instructions…"), and any markup it emitted would be a stored-XSS vector of its own.

Security control. Two layers. (1) Output: the AI reply is rendered with textContent, never innerHTML, so markup in the reply cannot execute. (2) Input: the Worker re-validates the entire payload server-side against a strict schema — probability must be 0–1, label must be exactly "Phishing" or "Legitimate", contribution deltas must be finite and in −1…1, and feature names must appear in a hard whitelist of the 19 dataset features. Anything else is rejected with HTTP 400 before Gemini is ever called.

Mitigation. The prediction data is passed to Gemini inside a delimited <model_output> block, and the system prompt instructs the model to treat that block as untrusted data rather than as instructions. The AI is explicitly forbidden from producing its own verdict, from claiming to have visited the URL, and from asserting the site is safe — it must state its output is an explanation of the model's statistical prediction, not proof of safety.

Security improvement. The static UI label that marks the text as "the model's explanation, not proof the site is safe" is written by the application, not the model, so it cannot be edited by a prompt-injection attempt. Escaping the reply against a strict CSP and adding automated adversarial-URL test cases would strengthen this further.

Risk 3 — Secret exposure

Security problem. A naive design would put the Gemini API key in front-end JavaScript, exposing it to anyone who views the page source.

Security control. The key lives only as a Cloudflare Worker secret (env.GEMINI_API_KEY) on the server side. The browser only ever calls the Worker's public URL.

Mitigation. The Worker's CORS allow-list restricts which origins may call it, and its responses are asserted never to contain the key. The experiment script uses no API key at all — it only calls the public Worker endpoint.

Security improvement. Adding per-IP rate limiting on the Worker would reduce abuse of the free explanation endpoint.

The malicious-string check is automated and repeatable: node Midterm/Phishing-Website-Detection/tests/verify-explanation.mjs runs it along with the sanitization, prompt-injection and error-handling checks.

Limitations and Future Improvements

Current limitations:

  • The hybrid explanation layer works, but the deployed Worker returned real Gemini errors (HTTP 502) on 4 of 10 explanations during the experiment run, and successful responses took 6–18 seconds. Reliability and latency are genuine costs of the explanation layer; the classifier itself is unaffected because it runs locally.
  • The grounding measurement is an automated lexical check, which undercounts because large language models phrase the same idea many ways. Manual reading was needed to correct two false "verdict disagreement" flags and five false "missing caveat" flags. A stronger metric (semantic similarity, or human rating) is needed for trustworthy grounding numbers.
  • This experiment is not a user study. It shows the explanations are textually consistent with the model's real votes and contributions. It does not demonstrate that people actually understand phishing better — no claim of improved human comprehension is made from these results.
  • Only 10 held-out examples were tested (a deterministic selection), so the grounding and failure rates are indicative, not statistically powered.
  • URL-based features alone cannot detect phishing that uses valid certificates or compromised legitimate sites, and the dataset is a fixed snapshot that may not reflect newly created phishing techniques.

Future improvements:

  • Conduct a real user study to measure whether explanations improve comprehension
  • Replace the lexical grounding check with semantic or human-rated evaluation, and test more than 10 examples
  • Add retry/backoff or a fallback model on the Worker to reduce the 502 failure rate and latency
  • Add page-content features beyond URL signals for stronger detection
  • Add per-IP rate limiting and a stricter CSP to harden the explanation endpoint

Reproducibility

Every result on this page can be regenerated from this repository. There are two experiments, each with its own entry point.

Experiment 1 — Classifier comparison (notebook)

Runs in Google Colab or locally. It loads the Web Page Phishing Dataset, replicates the Decision Tree / Random Forest baseline, trains the four additional models, runs 5-fold cross-validation, and writes the results JSON and accuracy chart. 

cd Assignment6
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
jupyter notebook Hybrid_Phishing_Experiments.ipynb   # run all cells

Output: results/experiments_results.json and results/model_accuracy_comparison.png. (A ready-made .venv already exists in this clone; it is not committed to git.)

Experiment 2 — Random Forest alone vs + AI explanation

A dependency-free Node script (Node 18+). It loads the real exported Random Forest and the production inference code from the Midterm site, runs it on 10 held-out rows, cross-checks each prediction against scikit-learn, sends each to the deployed mission-comms-chatbot Worker for an explanation, and records grounding, response time and failures. 

cd Assignment6
node experiments/run_hybrid_experiment.mjs

Output: results/hybrid_experiment_results.json. It calls only the Worker's public URL — no API key is used or exposed, since the Worker holds the Gemini key server-side. Because it queries a live service, response times and the exact failure count can vary between runs; the classifier's predictions will not.

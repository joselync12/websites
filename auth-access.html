Assignment 4 – Authentication & Access Control

Interactive Educational Demo of Authentication and Role-Based Access Control

1. Key Concepts

Authentication — "Who are you?"

Authentication is the process of verifying the identity of a user before granting access to a system. It answers the question: "Are you really who you claim to be?" Authentication typically involves credentials such as a username and password, multi-factor authentication (MFA), biometrics, or security tokens.

In a web application, authentication occurs when a user provides their credentials through a login form. The system verifies these credentials against stored data and, if valid, grants access to the application.

Authorization — "What are you allowed to do?"

Authorization is the process of determining which resources and actions an authenticated user has permission to access. It answers the question: "What are you permitted to do?" Authorization is based on the user's role, permissions, and policies defined by the application.

For example, a regular user may be authorized to view and edit their own profile, while an administrator may be authorized to manage users, view security logs, and manage website content. Authorization is enforced after authentication — you must first prove who you are before the system determines what you can do.

2. Authentication & Authorization Flow

The following diagram shows the flow from user login to role-based dashboard:

User → Login → Authentication → Role Check → Authorization → User/Admin Dashboard

Step 1: The user provides credentials (username and password) through the login form.
Step 2: The system verifies the credentials (authentication).
Step 3: The system determines the user's role (role check).
Step 4: The system grants access based on the role's permissions (authorization).
Step 5: The user sees a dashboard with actions appropriate for their role.

5. Production Implementation

In a real production environment, authentication and access control would be implemented with the following security measures:

Server-Side Authentication

Credentials are verified on the server, never in the browser. The server compares the provided password against a hashed version stored in the database. Client-side JavaScript should never be the only line of defense.

Password Hashing

Passwords are never stored in plaintext. They are hashed using a strong, slow hashing algorithm such as bcrypt or Argon2 with a unique salt for each password. This makes it computationally infeasible to recover passwords even if the database is compromised.

Secure Sessions

After successful authentication, the server creates a session and sends a session token to the client via a secure, HTTP-only cookie. The cookie is marked with Secure and SameSite attributes. Sessions have a timeout and are invalidated on logout. Session tokens are rotated periodically.

HTTPS (TLS 1.3)

All communication between the client and server is encrypted using TLS 1.3. This prevents eavesdropping, tampering, and man-in-the-middle attacks. The server enforces HTTPS via HSTS (HTTP Strict Transport Security) headers.

Database Access Controls

The database enforces access controls at multiple levels. The application connects using a database account with least privilege — only the permissions required for the application's queries. All queries use parameterized statements to prevent SQL injection. Sensitive data is encrypted at rest using AES-256.

Role-Based Access Control (RBAC)

Authorization is enforced on the server side for every request. The user's role is determined from their session, and the server checks whether that role has permission to perform the requested action. The principle of least privilege is applied — users have only the permissions they need.

Additional Security Measures

  • Multi-factor authentication (MFA) — requires a second factor beyond the password
  • Rate limiting — prevents brute force attacks on login endpoints
  • Account lockout — locks accounts after repeated failed login attempts
  • Audit logging — records all authentication and authorization events
  • CSRF protection — tokens prevent cross-site request forgery attacks
  • Content Security Policy (CSP) — prevents XSS and code injection

6. Conclusion

Authentication and authorization are two distinct but complementary security processes. Authentication verifies who you are, while authorization determines what you are allowed to do. Together, they form the foundation of access control in web applications.

In this educational demo, you experienced how a regular user and an administrator see different dashboards with different permissions. In a production system, these permissions would be enforced on the server side using secure authentication, password hashing, encrypted sessions, HTTPS, database access controls, and role-based access control.

Remember: This demo is a front-end simulation for educational purposes only. It does not perform real authentication and should not be used as a model for production security without implementing the server-side controls described in Section 5.

Assignment 3 – Secure Web Architecture

Defense-in-Depth Design for a Cybersecurity Awareness Web Application

1. Introduction

This document describes the secure web architecture for a proposed full-stack cybersecurity awareness web application. The application would extend the current static website with user accounts, dynamic content management, and interactive features while maintaining a strong security posture.

Current architecture: The existing website is a static site hosted on GitHub Pages. It consists of HTML, CSS, and JavaScript files served directly to the browser. There is no backend, database, authentication, or server-side processing.

Proposed architecture: The secure architecture described in this document represents a proposed future state where the application includes a frontend, web server, application layer, database, authentication, authorization, encryption, session management, and input validation.

2. Current vs. Proposed Architecture

Component Current (Static Site) Proposed (Full Application)
Frontend HTML, CSS, JavaScript HTML, CSS, JavaScript + Framework (React/Vue)
Web Server GitHub Pages (managed) Nginx/Apache (reverse proxy, load balancer)
Application Layer None (no backend) Node.js/Python (business logic, API endpoints)
Database None PostgreSQL/MySQL (encrypted, access-controlled)
Authentication None Multi-factor authentication, password hashing
Authorization None Role-based access control (RBAC)

4. Architecture Components

4.1 Frontend

Purpose: The frontend is the user-facing layer of the application. It renders the user interface, captures user input, and communicates with the backend via API calls.

How it fits: The frontend is the entry point for all user interactions. It sends requests to the web server and displays responses to the user.

Security controls:

  • Content Security Policy (CSP) headers to prevent XSS
  • Input sanitization before sending data to the server
  • HTTPS-only communication (no mixed content)
  • Output encoding to prevent DOM-based XSS
  • Rate limiting on client-side requests

4.2 Web Server

Purpose: The web server receives HTTP requests from clients, serves static files, and routes dynamic requests to the application layer.

How it fits: The web server is the gateway between the outside world and the internal application. It terminates TLS connections and forwards requests to the application layer.

Security controls:

  • TLS 1.3 encryption for all connections
  • Rate limiting and DDoS protection
  • Web Application Firewall (WAF) rules
  • Access logging and monitoring
  • Security headers (HSTS, X-Frame-Options, X-Content-Type-Options)

4.3 Application Layer

Purpose: The application layer contains the business logic. It processes requests, enforces authorization rules, and interacts with the database.

How it fits: The application layer sits between the web server and the database. It validates input, executes business rules, and returns responses.

Security controls:

  • Input validation and sanitization
  • Parameterized queries to prevent SQL injection
  • Role-based access control (RBAC) enforcement
  • Error handling that does not leak sensitive information
  • API rate limiting and throttling

4.4 Database

Purpose: The database stores persistent data such as user accounts, content, and application state.

How it fits: The database is the final layer of the architecture. It is accessed only by the application layer, never directly by the frontend or web server.

Security controls:

  • Encryption at rest (AES-256)
  • Access controls and least privilege
  • Parameterized queries only
  • Regular backups and disaster recovery
  • Database activity monitoring and auditing

4.5 Authentication

Purpose: Authentication verifies the identity of users before granting access to protected resources.

How it fits: Authentication is handled at the application layer. When a user logs in, the application verifies their credentials and creates a session.

Security controls:

  • Multi-factor authentication (MFA)
  • Password hashing (bcrypt/Argon2)
  • Brute force protection (rate limiting, account lockout)
  • Secure password reset flow
  • Account lockout after failed attempts

4.6 Authorization

Purpose: Authorization determines what an authenticated user is allowed to do.

How it fits: Authorization is enforced at the application layer. Every request is checked against the user's permissions before processing.

Security controls:

  • Role-based access control (RBAC)
  • Principle of least privilege
  • Server-side authorization checks on every request
  • Resource-level access control
  • Deny-by-default policy

4.7 Encryption

Purpose: Encryption protects data in transit and at rest from unauthorized access.

How it fits: Encryption is applied at multiple layers. TLS protects data between the user and server. Encryption at rest protects data in the database.

Security controls:

  • TLS 1.3 for all data in transit
  • AES-256 encryption for data at rest
  • HTTP Strict Transport Security (HSTS)
  • Certificate management and rotation
  • Secure key management (HSM or key vault)

4.8 Session Management

Purpose: Session management maintains user state across multiple requests after authentication.

How it fits: Sessions are created at the application layer after successful authentication. The session token is stored securely in the user's browser.

Security controls:

  • Secure, HTTP-only cookies
  • Session timeout and expiration
  • Session token rotation
  • CSRF protection tokens
  • Session invalidation on logout

4.9 Input Validation

Purpose: Input validation ensures that all data entering the system is safe and conforms to expected formats.

How it fits: Input validation is performed at multiple layers. The frontend validates for user experience. The application layer validates for security.

Security controls:

  • Allowlist-based validation
  • Type checking and format validation
  • Length limits on all inputs
  • Output encoding before rendering
  • Server-side validation (never trust client-side only)

5. How Security Is Incorporated Into the Architecture

Security is incorporated into the architecture using a defense in depth approach. This means multiple layers of security controls work together to protect the application. If one layer fails, others still provide protection.

Defense in Depth

The architecture implements security at every layer:

  • Frontend: Input sanitization, output encoding, CSP headers
  • Web Server: TLS encryption, rate limiting, WAF, security headers
  • Application Layer: Input validation, authorization checks, error handling
  • Database: Encryption at rest, access controls, parameterized queries

Least Privilege

Each component has only the access it needs to function. The database user used by the application has only the permissions required for the application's queries. Users have only the permissions required for their role.

Separation of Duties

Different components handle different responsibilities. The web server handles TLS termination and routing. The application layer handles business logic and authorization. The database handles data storage. No single component has all the responsibility.

Fail Securely

When something goes wrong, the system defaults to denying access. Error messages are generic and do not reveal internal details. Failed authentication attempts trigger account lockout.

Security by Design

Security is built into the architecture from the start, not added as an afterthought. Every component is designed with security in mind. The architecture assumes that attackers will try to exploit it and implements controls to prevent, detect, and respond to attacks.

6. Conclusion

The proposed secure web architecture provides a robust defense in depth for the cybersecurity awareness web application. By implementing security controls at every layer — from the frontend to the database — the application can protect against a wide range of threats while maintaining usability and performance.

The current static GitHub Pages website does not have a database, authentication system, or backend. The architecture described in this document represents the proposed future state of the application and demonstrates how security would be incorporated as the application evolves.

Key security principles applied throughout the architecture include defense in depth, least privilege, separation of duties, fail securely, and security by design. These principles ensure that the application remains secure as it grows and new features are added.

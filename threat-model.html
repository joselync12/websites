Assignment 2 – Website Threat Model

STRIDE Analysis for a Cybersecurity Awareness Website

1. Introduction

This document presents a threat model for a personal cybersecurity awareness website using the STRIDE methodology. The website is a static site hosted on GitHub Pages that educates visitors about phishing awareness and showcases the builder's skills and security knowledge.

Current architecture: The website is a fully static site with no backend, database, or authentication. All content is served directly from HTML, CSS, and JavaScript files.

Proposed/future architecture: The Web Server, Application, Database, and Authentication components described in this document represent a proposed future architecture where the website may include user accounts, dynamic content, and server-side processing.

3. STRIDE Threat Model

STRIDE is a threat modeling framework developed by Microsoft. Each letter represents a category of security threat:

  • S — Spoofing: Impersonating something or someone else
  • T — Tampering: Modifying data or code
  • R — Repudiation: Claiming to have not performed an action
  • I — Information Disclosure: Exposing information to unauthorized parties
  • D — Denial of Service: Making a system unavailable
  • E — Elevation of Privilege: Gaining unauthorized access to higher privileges

3.1 Spoofing

Spoofing involves an attacker impersonating a legitimate user, system, or component to gain trust or access.

Threat Risk to Website Security Mitigation
Phishing clone of website Attackers create a fake version of the site to trick visitors into revealing information or downloading malware. Use a custom domain, enable HTTPS (GitHub Pages provides this), and educate visitors to verify the URL.
DNS spoofing Attackers redirect visitors from the legitimate site to a malicious clone by poisoning DNS records. Use DNSSEC, enable HSTS headers, and rely on GitHub Pages' built-in DNS infrastructure.
Fake login page (future) If authentication is added, attackers could create a fake login page to steal credentials. Implement multi-factor authentication (MFA), use HTTPS exclusively, and display a user-specific image or phrase during login.
Chatbot impersonation An attacker could manipulate the chatbot's keyword matching to provide misleading or harmful responses. Keep chatbot responses generic and pre-written, never share sensitive info, and validate all inputs.

3.2 Tampering

Tampering involves unauthorized modification of data, code, or configuration.

Threat Risk to Website Security Mitigation
Client-side code modification Users could modify HTML/CSS/JS in browser dev tools to alter content or bypass restrictions. This is inherent to client-side code. Move critical logic to the server side in the future and implement server-side validation.
Content injection via URL parameters If URL parameters are added without sanitization, attackers could inject malicious content. Validate and sanitize all input, use allowlists, and implement Content Security Policy (CSP) headers.
GitHub repository tampering If an attacker gains access to the GitHub repo, they could modify the site's source code. Enable two-factor authentication (2FA) on GitHub, use branch protection rules, and limit repository collaborators.
Dependency tampering If third-party libraries are added, attackers could compromise them to inject malicious code. Minimize dependencies, audit all third-party code, use Subresource Integrity (SRI), and pin dependency versions.

3.3 Repudiation

Repudiation involves a user denying that they performed an action, with no way to prove otherwise.

Threat Risk to Website Security Mitigation
Lack of audit trail The current static site has no server-side logging, so there is no record of who accessed what. If a backend is added, implement comprehensive logging of all user actions, authentication events, and data access.
Chatbot conversation denial A user could claim they never received specific information from the chatbot. Currently, conversations are not stored. If logging is added, ensure chatbot interactions are recorded with timestamps.
Non-repudiation failure (future) If user accounts are added, users could deny actions like posting content or changing settings. Implement digital signatures, maintain immutable audit logs, and require authentication for all state-changing actions.

3.4 Information Disclosure

Information disclosure involves exposing sensitive data to unauthorized parties.

Threat Risk to Website Security Mitigation
Sensitive data exposure Personal information such as address, phone number, student ID, or financial data could be accidentally published. Follow data minimization principles. Only publish information that is necessary and appropriate for a public portfolio.
Source code exposure All HTML/CSS/JS is visible in browser dev tools. Hardcoded secrets would be exposed. Never hardcode API keys, passwords, or secrets in client-side code. Use environment variables and server-side proxies for sensitive operations.
Chatbot data leakage The chatbot could inadvertently reveal sensitive information through its responses. Ensure all chatbot responses are pre-written and reviewed. Never include personal or sensitive data in chatbot answers.
localStorage exposure Theme preferences and other data stored in localStorage could be accessed by malicious scripts. Only store non-sensitive data in localStorage. Implement Content Security Policy (CSP) to prevent unauthorized script execution.
Error message leakage (future) Detailed error messages could reveal database structure, file paths, or server configuration. Use generic error messages for users. Log detailed errors server-side only and never expose them to the client.

3.5 Denial of Service

Denial of Service (DoS) attacks aim to make a system unavailable to legitimate users.

Threat Risk to Website Security Mitigation
DDoS attack Attackers flood the server with traffic, making the site unavailable. GitHub Pages provides built-in DDoS protection. For future architectures, use a CDN, rate limiting, and traffic filtering.
Resource exhaustion The starfield animation with 120 animated stars could cause performance issues on low-end devices. Use CSS animations (already implemented), respect prefers-reduced-motion, and optimize animation performance.
Chatbot spam A user could send many messages to the chatbox, potentially degrading performance. Implement client-side rate limiting, debounce input, and limit message length.
GitHub Pages outage If GitHub Pages experiences downtime, the site becomes unavailable. Consider a backup hosting provider or a static site mirror. Monitor site uptime.

3.6 Elevation of Privilege

Elevation of privilege involves an attacker gaining access to higher-level permissions than they should have.

Threat Risk to Website Security Mitigation
Unauthorized repository access An attacker gains write access to the GitHub repo and modifies the site. Enable 2FA, use a strong unique password, enable branch protection, and limit collaborators.
Privilege escalation (future) If user roles are added, an attacker could escalate from a regular user to an administrator. Implement role-based access control (RBAC), follow the principle of least privilege, and validate permissions server-side for every request.
Session hijacking (future) An attacker steals a user's session token to impersonate them. Use secure, HTTP-only cookies, implement session expiration, rotate session IDs, and bind sessions to IP addresses.
GitHub Actions compromise (future) If CI/CD pipelines are added, attackers could modify build processes to inject malicious code. Audit workflow files, pin action versions, use least-privilege tokens, and review all pipeline changes.

4. Specific Attack Categories

4.1 Authentication Attacks

Applicability: The current website has no authentication system. These attacks apply to the proposed/future architecture where user accounts may be added.

Attack Risk Mitigation
Brute force Attacker tries many password combinations to gain access. Implement rate limiting, account lockout after failed attempts, CAPTCHA, and strong password policies.
Credential stuffing Attacker uses leaked credentials from other breaches to access accounts. Implement multi-factor authentication (MFA), monitor for breached credentials, and enforce unique passwords.
Session hijacking Attacker steals session tokens to impersonate a logged-in user. Use secure HTTP-only cookies, implement session timeout, rotate tokens, and use HTTPS exclusively.

4.2 Authorization Attacks

Applicability: The current website has no authorization system. These attacks apply to the proposed/future architecture where user roles and permissions may be added.

Attack Risk Mitigation
Privilege escalation A regular user gains admin privileges. Implement role-based access control (RBAC), validate permissions server-side, and follow least privilege.
Insecure direct object references (IDOR) Attacker accesses other users' data by modifying object IDs in requests. Implement access control checks for every request, use indirect references, and validate ownership server-side.
Missing function-level access control Attacker accesses admin functions by guessing URLs or endpoints. Enforce authorization checks on every endpoint, never rely on client-side hiding, and return consistent error messages.

4.3 SQL Injection

Applicability: The current website has no database. These attacks apply to the proposed/future architecture where a database may be added.

Attack Risk Mitigation
Classic SQL injection Attacker injects SQL code through input fields to manipulate database queries. Use parameterized queries/prepared statements, an ORM, and input validation. Never concatenate user input into SQL.
Blind SQL injection Attacker extracts data by observing boolean or time-based responses. Use parameterized queries, implement WAF rules, and monitor for unusual query patterns.
NoSQL injection Attacker injects malicious queries into NoSQL databases like MongoDB. Validate and sanitize all input, use type checking, and avoid passing raw user input to database queries.

4.4 Cross-Site Scripting (XSS)

Applicability: XSS is relevant to both the current and future architecture. The current chatbox uses textContent which is safe, but future features could introduce XSS risks.

Attack Risk Mitigation
Stored XSS Malicious script is stored on the server and executed when users visit the page. Sanitize all user input before storing, use output encoding, and implement Content Security Policy (CSP).
Reflected XSS Malicious script is reflected off the server in response to a crafted request. Validate and sanitize all input, use output encoding, and implement CSP headers.
DOM-based XSS Malicious script executes due to unsafe DOM manipulation on the client side. Use textContent instead of innerHTML, avoid eval(), and sanitize all data before DOM insertion.

4.5 Denial-of-Service (DoS) Attacks

Applicability: DoS attacks are relevant to both the current and future architecture.

Attack Risk Mitigation
DDoS Attackers flood the server with traffic to make the site unavailable. Use a CDN, implement rate limiting, use traffic filtering, and rely on GitHub Pages' built-in DDoS protection.
Resource exhaustion Attackers consume server resources (CPU, memory, bandwidth) to degrade performance. Implement rate limiting, set resource quotas, use caching, and monitor resource usage.
Slowloris (future) Attacker opens many connections and holds them open to exhaust server connections. Set connection timeouts, limit concurrent connections, and use a reverse proxy.

4.6 Credential Attacks

Applicability: The current website has no credential system. These attacks apply to the proposed/future architecture where user accounts may be added.

Attack Risk Mitigation
Brute force Attacker tries many password combinations. Implement rate limiting, account lockout, CAPTCHA, and strong password requirements.
Password spraying Attacker tries a few common passwords against many accounts. Enforce unique passwords, implement MFA, and monitor for distributed login attempts.
Keylogging Malware captures keystrokes to steal credentials. This is a client-side threat. Educate users to use antivirus software and avoid suspicious downloads.

4.7 Data Leakage

Applicability: Data leakage is relevant to both the current and future architecture.

Threat Risk Mitigation
Sensitive info in source code API keys, passwords, or personal data hardcoded in client-side code. Never hardcode secrets. Use environment variables and server-side proxies. Audit code before publishing.
Sensitive info in chatbot Chatbot responses could contain personal or sensitive data. Review all chatbot responses. Only include information that is appropriate for public viewing.
Sensitive info in comments HTML/CSS/JS comments could reveal internal details or sensitive information. Remove or sanitize comments before publishing. Use minification to strip comments in production.
Sensitive info in error messages (future) Detailed error messages could reveal server configuration or database structure. Use generic error messages for users. Log detailed errors server-side only.

4.8 Unauthorized Access

Applicability: Unauthorized access is relevant to both the current and future architecture.

Threat Risk Mitigation
Unauthorized repository access Attacker gains write access to the GitHub repo and modifies the site. Enable 2FA, use strong passwords, enable branch protection, and limit collaborators.
Unauthorized deployment (future) Attacker deploys malicious code to the hosting platform. Use deployment keys, implement CI/CD security, require code review, and monitor deployment logs.
Domain hijacking Attacker gains control of the domain registrar account. Enable domain registrar lock, use strong credentials, enable 2FA on the registrar account, and monitor domain settings.
Unauthorized admin access (future) Attacker gains access to admin panels or management interfaces. Implement strong authentication for admin panels, use IP allowlisting, enable MFA, and log all admin actions.

6. Recommendations

  1. Enable two-factor authentication (2FA) on GitHub — Protects against unauthorized repository access, which is the highest-risk threat to the current static site.
  2. Continue using textContent instead of innerHTML — Prevents DOM-based XSS vulnerabilities in the chatbox and future features.
  3. Exclude all sensitive personal information — Never publish address, phone number, student ID, passwords, or financial data on the site.
  4. Add Content Security Policy (CSP) headers — Prevents XSS and code injection attacks by restricting which scripts can execute.
  5. Audit code before publishing — Ensure no secrets, API keys, or sensitive data are hardcoded in client-side code.
  6. Use a custom domain — Adds legitimacy, makes phishing harder, and provides more control over DNS settings.
  7. Monitor GitHub repository activity — Detect unauthorized changes early by enabling notifications and reviewing access logs.
  8. Implement rate limiting for the chatbox — Prevent abuse and resource exhaustion from excessive messages.

7. Conclusion

This threat model analyzed the security posture of a personal cybersecurity awareness website using the STRIDE methodology. The current website is a static GitHub Pages site with no backend, database, or authentication, which significantly reduces the attack surface. The primary risks are unauthorized repository access and phishing clones, which can be mitigated through GitHub security best practices.

The proposed future architecture — including a web server, application logic, database, and authentication system — introduces additional threats that must be addressed with proper security controls. By following the recommendations in this document, the website can maintain a strong security posture as it evolves.

The minimalist, dependency-free approach of the current site is itself a security strength: fewer components mean fewer vulnerabilities. Maintaining this philosophy while adding features will be key to keeping the site secure.
